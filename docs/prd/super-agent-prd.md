## 0. 一页摘要

**产品一句话：** 企业把资料和系统接进来，超级智能体读懂企业后推荐数字员工和工具；员工在对话里派活，邮件和日期也能自动触发工作流；需要人决定的事进“待我处理”，每一步都有依据、审批和回读证据。

**部署形态：** 一个容器镜像，前后端一体，部署在客户的 Azure 订阅里，一个企业一套（单租户部署，数据模型保留 tenant_id 以便以后做多租户）。

**模型接入：** 管理员在 Setup 页填一个 API Key，选服务商（Anthropic Claude / OpenAI GPT / Azure OpenAI），从“服务商模型列表 ∩ 平台已测试白名单”中选择。Key 只存 Key Vault。“一个 Key”只指模型服务商凭据；邮件、SharePoint、数据库等连接器各自另行授权，不能用模型 Key 代替。

**MVP 必需 Azure 服务（7 项）：** Container Apps、Container Registry、PostgreSQL Flexible Server（含 pgvector）、Blob Storage、Key Vault、Entra ID、Application Insights。其余按需。

**MVP 范围：** Setup → 知识源插件（本地文件、只读数据库，邮件与 SharePoint 为第二批）→ 分析推荐 → 数字员工与工具卡 → SOP 与人工/日期触发（邮件触发为第二批）→ 指挥室对话 → 待我处理（7 类）→ 审计。

## 1. 产品定位与范围

### 1.1 要解决的问题

1. 企业知识散在文件、邮件、SharePoint 和业务数据库里，AI 无法“先读懂企业再干活”。
2. 现有 AI 助手只能聊天，不能持续推进跨天、跨系统的事项，也不记得事情做到哪一步。
3. 敏感操作（系统录入、对外发信、资金）需要人确认，但确认的内容格式各系统不同，缺统一的人工确认界面。
4. 企业缺少的系统能力（没有 API 的网页系统、内部数据库）需要快速变成可控、可审计的工具。

### 1.2 目标用户与角色

| 角色 | 典型人员 | 能做什么 | 不能做什么 |
|---|---|---|---|
| 管理员 | IT / 实施顾问 | Setup（模型、Key、连接器凭据）、用户与角色、部署健康 | 默认不处理业务工作项 |
| 企业负责人 | 老板 / 运营负责人 | 确认知识来源、调整组织草案、发布 SOP 和工具版本、审批高风险动作、看异常 | 不能绕过审批规则本身 |
| 员工 | 业务人员 | 指挥室派活、处理分配给自己的“待我处理”、个人工具账号绑定 | 看不到别人负责的事项和未授权来源 |
| 审核人 | 指定的复核人 | 复核交付、双人复核中的第二人 | 不能复核自己提交的内容 |
| 数字员工 | AI 岗位 | 在授权工具和知识范围内执行任务、回报结果 | 不能自行发布工具、扩大权限、批准自己的动作 |

页面入口沿用原型：负责人 7 个一级入口（指挥室、超级智能体、企业知识、数字员工、员工工具、待我处理、管理设置），员工 2 个入口（指挥室、我的工具，外加“待我处理”中属于自己的项）。Setup 位于“管理设置”下，仅管理员和企业负责人可见。

### 1.3 MVP 范围与不做清单

**MVP 做：**

- Setup：模型服务商、Key、测试、模型选择、两档模型、用量上限。
- 知识源插件框架 + 首批插件：本地文件上传、只读数据库（PostgreSQL / SQL Server / MySQL）。
- 分析推荐：业务对象、SOP 候选、数字员工、工具，均带原文依据；人工可改，重分析只给差异。
- 数字员工：创建、编辑职责与提示词、绑定工具、在线状态。
- 工具卡全生命周期：占位 → 获取（安装现成 / 指定开发 / 导入脚本 / 数据库只读查询生成）→ 测试 → 发布 → 部署 → 安装 → 个人绑定 → 可用。
- SOP：图形查看与编辑、发布版本、人工 / 日期触发；邮件触发为第二批。
- 指挥室：连续对话、@数字员工、任务从对话产生、员工在同一对话回报。
- 待我处理：7 类人工工作项、4 种渲染器、按角色过滤。
- 审计：所有动作、审批、外部调用留痕。

**第二批（MVP 之后紧接）：** 邮件知识源与邮件触发（Microsoft Graph）、SharePoint 知识源、浏览器录制工具路线（browser 镜像）、PDF / 扫描件解析（Document Intelligence）、长事项与来件并回原事项、按项目数据计算日期、批量与收集步骤。

**明确不做：** 完整 BPMN 编辑器、通用低代码应用生成器、公开插件市场、支付钱包、AI 自主修改制度、AI 自主对外发信或付款（必须人工审批）。

## 2. 核心概念与名词

| 名词 | 定义 |
|---|---|
| 企业知识空间 | 一个企业的全部已确认知识，由多个“来源”组成 |
| 知识源插件 | 一种接入能力，例如“本地文件”“PostgreSQL 只读” |
| 连接 | 某企业对某插件的一次授权配置（凭据引用、范围） |
| 来源条目 | 连接下的具体文件、邮件、表，带版本和原始位置 |
| 本体 | 业务对象类型、实体与关系（项目、Lot、业主、发票…） |
| SOP | 已发布、有版本的工作流定义：触发、步骤、岗位、工具、审核、完成证据 |
| SOP 实例 | 一次 SOP 运行，固定 SOP 版本和知识快照 |
| 任务 | 实例中分给某数字员工的一步，或从对话产生的单次工作 |
| 数字员工 | AI 岗位：职责、提示词、允许的工具与知识范围、运行时连接 |
| 工具 | 有稳定 ID、契约（输入/输出/副作用/范围）、版本的能力 |
| 人工工作项 | 需要人处理的一件事，7 类之一，进入“待我处理” |
| 动作批准 | 对一次精确动作（对象 + 参数 + 载荷哈希）的授权 |

## 3. 功能模块详细说明

每个模块按“用户故事 → 页面与交互 → 业务规则 → 状态 → 异常 → 验收标准”描述。

### 3.1 Setup：模型服务商与 Key

**用户故事**

- 作为管理员，我只需填一个 API Key、选一个模型，系统就能工作。
- 作为企业负责人，我希望控制每月模型费用，超出时暂停而不是继续扣费。

**页面与交互**（管理设置 → Setup → 模型）

1. 选择服务商：`Anthropic（Claude）`、`OpenAI（GPT）`、`Azure OpenAI`。
   - 选 Azure OpenAI 时额外填写：Endpoint、API 版本、部署名（每个部署对应一个模型）。
2. 粘贴 API Key，点“测试连接”。
   - Key 只经后端测试，不在浏览器里直接调用服务商；请求和错误日志对 Key 脱敏。
   - 测试分三项，分别给出结果：① 认证（一次最小对话请求，用该模型允许的最小输出设置；推理类模型按服务商要求设置，不强行套用固定 token 上限）；② 模型列表（可选）；③ 工具调用格式。
   - 判定：只有认证失败才判“Key 无效”。模型列表接口失败或无列举权限，只提示“无法自动列出模型，请手填白名单 ID”，不判 Key 无效。
   - 通过且 Key Vault 写入成功后才激活（secret 名：`llm-provider-key`），页面只显示末 4 位与保存时间；写入失败则不激活。
   - 失败：显示服务商返回的错误类型（无效 Key / 额度不足 / 网络 / 区域不可用），Key 不保存。
3. 选择模型：
   - 可选列表 = 服务商模型列表接口返回的模型 ∩ 平台“已测试白名单”。白名单记录每个模型已通过的能力测试（对话、工具调用、结构化输出、流式），由我们随版本维护、可热更新。
   - 服务商列表里有、白名单里没有的新模型，显示为“未验证”，默认不可选；管理员可手动启用，启用前必须跑一遍能力测试。
   - 模型列表接口失败时，允许手动填写白名单内的模型 ID，并测试。
   - 列表接口返回成功，不代表该模型的推理、工具调用与本平台兼容，所以以能力测试为准。
   - 示例（2026-11-09 核验，仅为当天快照，不是永久承诺）：Anthropic 有 `claude-opus-5-5`（建议主模型）、`claude-sonnet-5-5`（均衡）、`claude-haiku-5-5`（建议经济模型）、`claude-fable-5-1`；OpenAI 官方目录当天列出 gpt-6 系列（如 gpt-6-astra、gpt-6.1-sol、gpt-6-luna，由 Codex 核对官方文档）。具体可选型号以接口返回和白名单为准。
   - Azure OpenAI 无模型列表可选时，以管理员填写的部署名为准，测试时校验部署存在。
   - 切换模型：记录切换前后的模型 ID 和时间；已发布 SOP 的验收结果标记为“模型已变更，待复核”。已在执行的任务继续用领取时快照里的模型，不中途换；新任务用新模型。负责人复核（重跑 SOP 门禁用例）通过后才清除“待复核”。
4. 两档模型（可选）：
   - 主模型：超级智能体规划、推荐、复杂任务。
   - 经济模型：批量抽取、分类、摘要。不填则与主模型相同。
5. 知识检索方式：
   - MVP 默认：PostgreSQL 关键词检索（中文用 `pg_trgm` 三元组相似度，英文用全文检索），不需要任何嵌入模型，单个 Claude Key 即可工作。Azure PostgreSQL 支持的扩展以实测为准【待核实】。
   - 可选增强一：服务商嵌入接口（选 OpenAI / Azure OpenAI 时可用）+ pgvector，做混合检索。
   - 可选增强二：本地嵌入模型。启用前必须固定模型与许可证、镜像增量大小、CPU/内存需求和重建索引耗时，并通过中英文检索评测。不作为首版必需。
   - 切换检索方式或嵌入模型会触发全量重建索引，页面需提示耗时与费用，并要求确认。
6. 用量与上限：显示本月 token 用量与估算费用（按后端维护的单价表，标“估算”）；可设月度上限和单任务上限。
   - 硬上限的实现方式（防止多个 worker 同时越过上限）：
     - 每次调用前，按“本次最大可计费量”在数据库里原子预留（单条 UPDATE，余额不足则拒绝）。最大可计费量 = 实测输入 token（调用前计数）+ 本次设置的输出上限（max output tokens，推理 token 计入其中的服务商按此计）+ 本次允许的工具费用上限。
     - 因为输出被参数封顶，实际计费不会超过预留。
     - 调用成功：按服务商返回的实际用量结算，退回差额。
     - 调用明确失败且服务商确认未计费：释放预留。
     - 超时或结果不明：预留保持冻结，直到按服务商用量记录对账后再结算或释放。
     - 某服务商存在单次请求参数无法封顶的计费项时，该服务商在 Setup 中标“软限额”，并显示可能超出的上界；只有能完全封顶的配置才显示“硬上限”。
7. 更换 Key（轮换）：
   1. 新 Key 先在服务端测试通过；
   2. 写入 Key Vault 新版本成功；
   3. 在一个数据库事务里把配置指向新版本，同时通知各进程清空 Key 缓存；切换的几秒内新调用短暂排队，不报错；
   4. 旧版本按保留策略在 Key Vault 中禁用（不是删除整个 secret，删除 secret 会影响所有版本）。
   - 页面提醒管理员：平台禁用旧版本，不等于在服务商处作废了旧 Key；需要到服务商后台撤销旧 Key。
8. 撤销 Key：配置置为“已撤销”，所有新模型调用停止；进行中的任务在下一次模型调用时进入“等待模型配置”；同样提醒到服务商后台撤销。

**业务规则**

- Key 永不写入数据库、日志、前端存储或模型上下文；数据库只存 Key Vault secret 名与版本、末 4 位、保存人、时间。
- 只有管理员和企业负责人能看到 Setup；员工端不可见。
- 每次调用记录：服务商、模型、输入/输出 token、耗时、关联任务 ID。
- 达到月度上限：新调用拒绝，已开始的单次调用允许完成；指挥室和“待我处理”给负责人一条提醒。

**数据出境提示（页面必须显示）**

- 选 Anthropic 或 OpenAI 直连 Key：请求内容发往该服务商，不在客户 Azure 内处理。
- 选 Azure OpenAI：按所选部署类型处理。Global 类型可能在全球任一区域处理，Data Zone 类型限定在数据区内，Standard（区域）类型在部署区域内处理。页面显示所选部署类型。
- 通过 Microsoft Foundry 使用 Claude：官方区分“Azure 托管”和“Anthropic 托管”两种方式，后者的数据可能离开 Azure。页面必须显示实际托管方式和部署类型，不能笼统写成“在 Azure 内处理”。依据：https://learn.microsoft.com/en-us/azure/foundry/foundry-models/concepts/claude-models-hosting-comparison 。可用区域与型号【待核实】。

**状态：** 未配置 → 测试中 → 已配置 → 轮换中 → 已配置；已配置 → 已撤销；另有“已达上限”“等待模型配置”（任务级）。

**异常**

| 情况 | 处理 |
|---|---|
| 服务商临时故障 / 限流 | 按退避重试（有上限）；仍失败则任务进入“等待模型”，不丢任务 |
| Key 被服务商作废 | 认证失败 → 配置标“Key 失效”，新调用停止，提醒管理员 |
| 所选模型被服务商下线 | 能力白名单标“停用”，提醒更换；进行中任务进入“等待模型配置” |
| Key Vault 不可用 | 使用进程内短时缓存（≤5 分钟）；超时后停止新调用并告警 |

**验收标准**

1. 未配置模型时，除 Setup 外所有需要模型的功能显示“请先完成模型设置”，不报错。
2. 错误 Key 测试失败、不保存；正确 Key 测试通过，数据库和日志中搜索不到 Key 原文。
3. 模型下拉 = 实时接口 ∩ 白名单；未验证模型默认不可选；接口失败时可手填白名单 ID 并测试。
4. Key Vault 写入失败时 Key 不激活；日志中无 Key 原文。
5. 达到上限后，新任务不再调用模型，负责人收到提醒。
6. 切换检索方式或嵌入模型需二次确认，并生成重建索引的后台任务。
7. 只配置一个 Claude Key（无嵌入接口）时，知识检索仍可用（关键词检索）。
8. 模型列表接口返回 403 时，Key 不被判无效，页面引导手填白名单 ID。
9. 硬上限配置下，多个 worker 并发调用（含人为制造超时）时，已计费总额不超过月度上限；超时调用的预留在对账前不被释放。软限额配置在页面明确标出。
10. Key 轮换过程中没有调用失败；旧版本在 Key Vault 中被禁用，页面提示到服务商撤销旧 Key。
11. 切换主模型后，进行中任务仍用旧模型完成；已发布 SOP 显示“待复核”。

### 3.2 企业知识与知识源插件

**用户故事**

- 作为负责人，我上传资料或接入数据库后，先确认哪些来源可用，超级智能体才开始分析。
- 作为员工，我检索知识时只看到自己有权看的内容，每条回答都能回到原文位置。

**三层模型：** 插件 → 连接 → 来源条目。

**插件统一接口（后端 TypeScript 接口，所有插件必须实现）**

```ts
interface KnowledgeSourcePlugin {
  manifest: {
    id: string; version: string; name: string;
    capabilities: { incremental: boolean; attachments: boolean; liveQuery: boolean; acl: boolean };
    permissions: string[];          // 声明需要的只读权限
  };
  testConnection(conn: ConnectionConfig): Promise<TestResult>;
  listItems(conn: ConnectionConfig, cursor?: string): Promise<{ items: SourceItemRef[]; nextCursor?: string }>;
  readItem(conn: ConnectionConfig, ref: SourceItemRef): Promise<SourceContent>;   // 文本/表结构/附件，带定位信息
  getAcl?(conn: ConnectionConfig, ref: SourceItemRef): Promise<AclResult>;
  liveQuery?(conn: ConnectionConfig, template: QueryTemplate, params: unknown): Promise<LiveFact>; // 仅数据库类
}
// listItems 返回的每个条目带 change: 'upsert' | 'deleted' | 'access_revoked'
// AclResult = { status: 'known', entries: AclEntry[] } | { status: 'unknown', reason: string }
// 所有方法失败时抛 SourceError { kind: 'auth' | 'scope' | 'throttled' | 'transient' | 'cursor_invalid' | 'not_found' | 'fatal', retryAfter? }
```

**同步语义（所有插件统一，可验收）**

| 情况 | 插件返回 | 平台处理 | 恢复条件 |
|---|---|---|---|
| 条目新增或修改 | change = upsert，新版本号 | 解析新版本；旧版本保留；引用它的推荐 / SOP 标“依据已变更” | 负责人复核后清除标记 |
| 条目删除 | change = deleted | 条目标“已删除”，立即停止用于检索和分析；保留历史版本供审计 | 无需恢复；如原系统恢复，作为新版本重新进入 |
| 条目撤权 | change = access_revoked | 立即从检索中移除；相关推荐标“依据不可用” | 权限恢复后重新同步并复核 |
| ACL 未知 | AclResult.status = unknown | 条目可列出但标“权限未知”，不参与检索、分析、推荐，也不能被引用 | 只有插件重新返回已知 ACL 才能恢复。负责人不能用手工指定来代替未知的原 ACL；负责人只能在已知 ACL 的基础上进一步收窄可见范围 |
| 本批同步失败（transient / throttled） | 抛 SourceError | 不推进游标；按 retryAfter 或退避重试；本批已处理条目以内容哈希去重 | 重试成功后才推进游标 |
| 游标失效（cursor_invalid） | 抛 SourceError | 不推进游标；触发一次全量重新列举，与现有条目按 external_id + 内容哈希对账 | 全量对账完成后写入新游标 |
| 认证失败 / 范围被缩小（auth / scope） | 抛 SourceError | 连接标“需重新授权”，停止同步；该连接下所有条目立即暂停用于新的检索、分析、推荐和引用，已有回答中的引用显示“来源暂不可用” | 管理员重新授权并测试通过，且重新同步后的 ACL 为已知，才恢复使用 |

无论哪种情况，人工编辑过的推荐都不会被同步结果覆盖，只产生差异建议。

**首批插件**

| 插件 | 批次 | 范围设置 | 同步方式 | 特别规则 |
|---|---|---|---|---|
| 本地文件 | MVP | 上传的文件 | 一次性导入，可手动上传新版本 | 支持 txt、md、docx；PDF/扫描件需 Document Intelligence（第二批） |
| 只读数据库 | MVP | 库、表、列白名单；敏感列标记；行过滤条件 | 结构按需重新分析；当前值实时查询 | 见 3.2.1 |
| 历史邮件 | 第二批 | 邮箱、文件夹、时间范围 | 增量（Graph delta） | 只读；与“邮件触发”是两件事 |
| SharePoint / OneDrive | 第二批 | 站点、文档库、文件夹 | 增量（Graph delta），处理删除和撤权 | 保留原 ACL 与原文件链接 |

**页面与交互**（企业知识 → 来源）

1. “接入资料”按钮 → 选择插件 → 填写连接（凭据只填 Key Vault 引用或通过 OAuth，不允许粘贴连接串原文）→ 选择范围 → 预览条目（前 50 条，含权限）→ 提交。
2. 来源列表：每个来源显示插件、范围、条目数、最后同步、状态（待确认 / 已确认 / 同步失败 / 已撤回）。
3. 来源确认：负责人逐个确认。未确认来源不参与检索、分析和推荐。
4. 条目查看：原文、版本历史、被哪些推荐 / SOP / 回答引用。
5. 检索与问答：回答必须附来源条目与定位（文件第几页/行、表.列）；找不到依据时明确说“没有找到依据”，不编造。

**业务规则**

- 所有来源进入同一个来源目录和同一套确认流程。
- 条目带原系统 ACL；检索时按当前用户的身份过滤。ACL 未知的条目不能用于分析。
- 条目版本变更或删除：标记旧版本，相关推荐和 SOP 显示“依据已变更”，等待负责人复核。
- 知识源插件只授予“读取”；即使同一个服务商的连接器支持写入，知识接入也不能获得写权限。
- 条目的历史版本、条目原文片段在审计和执行记录中的展示，也按查看者当前对该条目的权限过滤；权限被撤销或变为未知后，历史正文同样不可见，只保留条目 ID、版本号和哈希。
- 来自资料的文字一律视为数据，不作为对系统的指令（提示注入防护，见 7.4）。

**3.2.1 只读数据库来源**

- 两种用途分开：
  1. 理解企业（开通时）：读取获准的表结构、外键、枚举值、少量统计与脱敏样本，用于本体和推荐。不整库导出。
  2. 查询当前事实（运行时）：通过“已审查询模板”参数化查询，返回结果带来源、结构版本、查询时间、范围、行数，标记为“当前事实”，不写入知识库，不变成规则。
- 只读三层保证：
  1. 数据库账号只有 SELECT（建议连只读副本）；客户 DBA 按文档创建。
  2. 查询网关：只允许已审模板；拒绝 DDL/DML、未登记函数、白名单外的列、超出行上限；只读事务；超时。
  3. 平台策略：表/列/行白名单、敏感列打码、按员工和项目过滤行、每次查询写审计。
- 表结构变更：撤回来源确认，旧分析标“依据已变更”，由此生成的查询工具暂停，直到复核。
- 从已确认的表结构可生成“只读查询工具”候选（工具获取的第 5 条路线），仍需走工具卡全部门禁。

**状态**

- 连接：草稿 → 测试通过 → 待确认 → 已确认 → 同步中 / 同步失败 → 已撤回。
- 条目：新 → 已解析 → 解析失败 → 已过期（有新版本）→ 已删除；另有“已撤权”“权限未知”。

**异常**：同步层面的删除、撤权、ACL 未知、批次失败、游标失效、认证失败，按上文“同步语义”表处理。此外：

| 情况 | 处理 |
|---|---|
| 文件解析失败（格式不支持、加密、超大） | 条目标“解析失败”并写原因，不进入检索；负责人可上传新版本或排除 |
| 数据库实时查询超时 | 返回“查询失败”，不拿缓存结果冒充当前值；可显示上次结果，但必须标出它的查询时间 |
| 检索无结果 | 回答“没有找到依据”，不编造 |

**验收标准**

1. 未确认来源时，“分析推荐”按钮不可用。
2. 数据库连接无法粘贴连接串原文，只能选择 Key Vault 引用。
3. 对只读来源发起写语句、未登记函数、越权列，网关全部拒绝并写审计。
4. 实时查询结果显示查询时间与范围；数据变化后旧结果标“已过期”。
5. 员工检索不到其无权访问的条目（用两个不同权限的账号验证）。
6. 每条问答回答都带可点击的来源定位。
7. 模拟条目删除、撤权、ACL 未知、游标失效四种情况，平台行为与“同步语义”表一致；同步失败时游标不前进。

### 3.3 分析推荐：业务对象、SOP、数字员工、工具

**用户故事：** 作为负责人，确认来源后，我希望系统一次给出“组织草案”：需要哪些数字员工、用哪些工具、有哪些流程，每条都告诉我依据在哪。

**流程**

1. 负责人点“开始分析”（或来源确认后自动提示）。
2. 后台分阶段执行，前端实时显示进度：解析 → 抽取对象与规则 → SOP 候选 → 推荐员工 → 推荐工具。每阶段完成即可查看结果。
3. 组织草案页：左列数字员工，右列工具与能力，中间显示“谁用哪个工具、参与哪个 SOP”的关系。
4. 每条推荐可展开查看依据（来源条目 + 定位 + 原文片段）和模型置信说明。

**人工调整规则**

- 员工：接受、改名、改职责与提示词、合并、删除、手动新建。手动新建的标记“人工创建 · 无知识依据”。
- 工具：先查已有能力目录（企业已安装工具、可用连接器 / MCP / Skill）；匹配到的显示“已验证存在”或“可能可用”；没有的建“占位”（见 3.5）。
- 人改过的项锁定。补充资料后重新分析，只产生差异建议（新增、建议修改、冲突），不覆盖人工修改；人删除的项不会被重新加回。
- 删除或合并员工前，显示受影响的 SOP 节点和工具，必须重新指派后才能确认。
- 推荐只是草案：创建员工不会自动连接运行时、不会授予工具或账号；确认 SOP 候选不会自动启用触发器。

**模型使用：** 主模型做规划与推荐；经济模型做逐条抽取。抽取结果用结构化输出（JSON Schema 约束），校验失败的条目重试一次，仍失败则标“待人工补充”。

**状态**

- 分析运行：排队 → 运行中（按阶段：解析 / 抽取 / SOP / 员工 / 工具）→ 已完成 / 部分完成 / 失败 / 已取消。
- 单条推荐：建议 → 已接受 / 已修改（人工锁定）/ 已合并 / 已删除 / 冲突待定。
- 组织草案：草稿 → 已确认（生成未连接的员工和工具占位）。

**异常**

| 情况 | 处理 |
|---|---|
| 某一阶段模型调用失败 | 该阶段标“失败”，已完成阶段的结果保留；可只重跑失败阶段 |
| 达到模型费用上限 | 运行暂停在当前阶段，标“因上限暂停”；提高上限后从断点继续 |
| 来源在分析中途变更或撤回 | 本次运行标“依据已变更”，结果仍可查看但不能确认，需重新分析 |
| 新分析结果与人工修改冲突 | 生成“冲突待定”项，由负责人选择，不自动覆盖 |
| 抽取结果两次校验失败 | 该条目标“待人工补充”，不阻断其他条目 |

**验收标准**

1. 每个推荐的员工和工具至少有一条可定位依据，或标“人工创建”。
2. 重分析后，人改过的名称和职责保持不变，差异以建议形式出现。
3. 删除一名员工后重分析，该员工不会被重新推荐。
4. 推荐的工具中，已存在的与占位的明确区分。
5. 人为让“推荐工具”阶段失败后，前面阶段的结果仍可查看；只重跑失败阶段即可完成。
6. 分析中途撤回一个来源，本次结果不能被确认。

### 3.4 数字员工

**用户故事：** 作为负责人，我能看到每个数字员工负责什么、用什么工具、现在是否在线、做了哪些事。

**数字员工属性**

| 字段 | 说明 |
|---|---|
| 名称、职责 | 来自推荐或人工编辑 |
| 系统提示词 | 可编辑，带版本 |
| 模型档位 | 默认 / 主模型 / 经济模型 |
| 知识范围 | 可检索的来源与项目范围 |
| 已安装工具 | 工具版本 + 本员工的账号绑定与范围 |
| 运行方式 | 平台托管 worker（MVP 默认）/ 外部 Agent（第二批，经 MCP 或适配器连接） |
| 负责人 | 对应的人类负责人 |
| 状态 | 未连接 / 在线 / 执行中 / 等待授权 / 已暂停 / 故障 |

**业务规则**

- 每次领取任务时，记录执行身份快照（提示词版本、工具版本、账号、范围）；执行动作前重新检查，有变化则停止新动作。
- 暂停优先：人工暂停的员工不会被任何触发自动唤醒。
- 员工只能使用自己已安装、已绑定、可用的工具；不能借用其他员工的凭据。

**状态**：未连接 → 在线 ⇄ 执行中；任一状态 → 已暂停（人工）→ 在线；在线 / 执行中 → 等待授权（工具或账号失效）/ 故障（连续失败）。

**异常**

| 情况 | 处理 |
|---|---|
| 执行中工具授权被撤销 | 停止新动作；已提交的外部动作按结果对账；任务进入“等待授权” |
| 连续多次模型或工具失败 | 员工标“故障”，不再领新任务；生成人工工作项给负责人 |
| 员工被删除或合并 | 必须先把它的 SOP 节点和进行中任务重新指派，否则不允许删除 |
| 外部 Agent 断线（第二批） | 标“未连接”；它领取的任务租约到期后回队列，不会两个执行者同时有效 |

**验收标准**

1. 修改提示词产生新版本，进行中的任务保留旧版本快照。
2. 撤销某工具的授权后，该员工的新动作立即被拒绝。
3. 暂停的员工不接新任务，恢复后不会补跑暂停期间的触发（除非负责人选择补跑）。
4. 连续失败达到阈值后员工变为“故障”，负责人在“待我处理”收到工作项。
5. 有进行中任务的员工不能直接删除。

### 3.5 工具卡全生命周期

**用户故事：** 作为负责人，缺少某个系统能力时，我先建一个占位，再选择怎么得到它，最后安全地装给需要的员工；整个过程在一张工具卡里完成，能看到走到哪一步。

**工具契约（占位时就要写下）**

| 字段 | 说明 |
|---|---|
| toolId、action | 稳定 ID 与动作标识，名称可改 |
| 用途、目标系统、副作用 | 只读 / 草稿 / 写入 / 对外 |
| 输入、输出 | 字段、类型、必填、单位、对象标识；输出含回读结构 |
| 范围与策略 | 允许的对象和字段、风险等级、是否需要精确批准 |
| 来源与验收用例 | 原资料定位；正常、冲突、失败、结果未知、重复等用例 |
| 使用员工、SOP 节点 | 谁要用 |
| 开发者、维护人、审核人 | 三者分别记录 |

**获取路线（同一张卡上切换）**

1. 安装现成：从能力目录选择连接器 / MCP Server / Skill，核对契约兼容。
2. 指定数字员工开发：选择开发岗位（需在线、有隔离工作区），生成开发任务，回报源码与产物版本。
3. 我们导入：上传脚本 / 包，或关联代码仓库。导入内容只存为待测产物，web 和 worker 从不执行它。
4. 浏览器录制（第二批，browser 镜像）：在隔离会话中由人登录目标测试环境，录制业务操作；参数化；加结果断言；回放验收。登录状态与凭据不进入工具包。
5. 数据库只读查询生成：从已确认表结构生成参数化查询模板。

**统一门禁（7 步进度条）**

占位 → 获取 → 测试 → 发布 → 部署 → 安装 → 可用

| 步骤 | 完成条件 | 失败时 |
|---|---|---|
| 占位 | 契约已确认 | — |
| 获取 | 有候选产物 | 回到获取 |
| 测试 | 在隔离环境跑完验收用例全部通过 | 不能发布；契约修改后旧测试作废 |
| 发布 | 审核人（不能是开发者）确认，版本固定 | — |
| 部署 | 执行环境健康检查通过 | 不能安装 |
| 安装 | 安装到指定员工 | — |
| 可用 | 该员工账号绑定与范围检查通过 | 账号变更后回到此步 |

已完成的步骤在卡上折叠为一行摘要（版本、环境、时间）；当前步高亮并写明卡点原因。

**隔离执行（导入、开发生成、录制的脚本）**

- 构建、测试和运行这类脚本，都在独立的“工具沙箱”中进行，不在 web / worker 里：独立的 Container App 或 Job，使用独立的托管身份。
- 沙箱身份没有主应用 Key Vault 的读取权限，也不能访问主数据库；运行时只拿到该工具本次调用所需的、由网关临时下发的最小凭据（单次、短时）。
- 网络出口按工具契约里的目标系统域名做白名单；限制 CPU、内存和运行时长。
- 产物（镜像或包）存到单独的仓库路径或存储容器，并记录摘要（哈希）；发布时固定摘要，部署时校验，不一致则拒绝。
- 依赖与代码扫描（第二批接入扫描工具）的结果作为“测试”步的一部分。

**工具未就绪时的业务处理：** SOP 中引用该工具的节点必须选择“阻塞等待”或“负责人批准的人工执行并回填”，才允许发布 SOP。工具就绪后，原请求恢复为“待执行”，不重复执行、不伪造结果。

**升级与回滚：** 新版本走完整门禁；进行中的实例继续用旧版本；可一键回滚到上一版本；契约不兼容时，依赖它的 SOP 提示重新验证。页面改版或健康检查失败时，相关动作自动暂停，并给维护人生成修复任务。

**状态**：即 7 步进度条（占位 / 获取 / 测试 / 发布 / 部署 / 安装 / 可用），另有“已暂停”（健康失败或人工）、“已停用”、“已取消”（仅未发布时可取消）。

**异常**

| 情况 | 处理 |
|---|---|
| 测试失败 | 停在“测试”，显示失败用例；修订后重测 |
| 契约在测试后被修改 | 旧候选与测试结果作废，回到“获取” |
| 部署健康检查失败 | 停在“部署”，不能安装；已安装的旧版本不受影响 |
| 运行中健康检查失败或目标页面改版 | 工具暂停；进行中的动作按结果对账；节点按 SOP 配置转阻塞或人工执行；给维护人派修复任务 |
| 指定的开发员工离线 | 不能指派；已指派的开发任务租约到期回队列 |
| 产物摘要与发布时不一致 | 拒绝部署并告警 |

**验收标准**

1. 占位工具不出现在任何员工的可调用工具列表中。
2. 测试未通过时“发布”不可用；开发者本人不能发布自己的工具。
3. 部署健康检查失败时“安装”不可用。
4. 改账号绑定后，状态从“可用”退回“安装”步骤。
5. 5 条路线都能走到“可用”。
6. 导入的脚本在 web / worker 进程中从未执行（审计与进程日志可证）；沙箱身份读取主 Key Vault 被拒绝。
7. 篡改产物后部署被拒绝。

### 3.6 SOP 与触发

**用户故事：** 作为负责人，我能看到企业的流程图，确认后发布；之后邮件、日期或人工都能按同一流程启动工作。

**SOP 定义内容：** 触发器（人工 / 日期 / 邮件）、步骤（岗位任务、工具动作、人工工作项、条件判断、等待）、每步的岗位与工具引用（引用本体与工具 ID，不复制）、审核人、完成证据、失败处理、业务约定（目标、输入、交付物、完成条件、异常负责人、审批与费用边界）。

**发布前校验（固定门禁用例）：** 正常读取、缺字段、超阈值、审批拒绝、重复事件、员工离线、暂停、外部结果不明、权限撤销、写入审批。未通过不能发布；配置变化后需重新校验。

**触发器**

| 类型 | 批次 | 规则 |
|---|---|---|
| 人工 | MVP | 指挥室对话或按钮启动 |
| 日期 | MVP | 保存 IANA 时区（如 Pacific/Auckland）、规则版本、补跑窗口、重叠策略；正确处理夏令时；默认关闭，需显式启用 |
| 数据驱动日期 | 第二批 | 日期来自本体字段（如 project.fy_end + N 个工作日），按项目分别计算 |
| 邮件 | 第二批 | Graph 订阅 + 定时补扫；按 tenant + source + event_id + sop_id 去重；邮件内容是数据，不是指令 |

**实例规则：** 每个实例固定 SOP 版本、知识快照、触发事件；发布新版本不改旧实例；同一事件不重复启动；结果不明先对账，不重复发信、下单或写入。

**状态**

- SOP 版本：草稿 → 校验中 → 校验通过 / 校验失败 → 已发布 → 已停用。配置改动使“校验通过”失效。
- 触发器：关闭 ⇄ 启用；启用 → 已暂停（来源撤回、员工缺失等）。
- 实例：运行中 → 等待（人工 / 外部 / 工具）→ 已完成 / 已取消 / 异常。

**异常**

| 情况 | 处理 |
|---|---|
| 宕机期间错过日期触发点 | 恢复后按补跑窗口与重叠策略处理；超出窗口的只记录“已错过”，不补跑 |
| 上一个实例未完成又到触发点 | 按重叠策略：跳过 / 排队 / 并行（默认跳过并记录）|
| 引用的工具或员工不可用 | 节点按 SOP 配置阻塞或转人工执行；不跳过节点 |
| 引用的知识来源被撤回 | 新实例不启动，触发器标“已暂停”，负责人复核 |
| 取消实例 | 阻止后续步骤；已发出的外部动作不撤回，只记录并提示人工处理 |

**验收标准**

1. 未启用的触发器不创建实例。
2. 同一封邮件 / 同一日期发生点重复输入，只产生一个实例。
3. 夏令时切换日的日期触发按当地时间正确执行一次。
4. 新版本发布后，旧实例仍显示旧版本号并按旧定义运行。
5. worker 停机跨过一个日期触发点后恢复：在补跑窗口内只补跑一次，窗口外记录“已错过”。
6. 校验未通过的 SOP 不能发布；发布后修改任一配置需要重新校验。

### 3.7 指挥室（对话）

**用户故事：** 作为负责人或员工，我在一个对话里和超级智能体讨论、@数字员工派活；任务从对话产生，结果回到同一对话。

**页面：** 页头一行（标题 + 副标题 + 操作）；主区为对话；右侧为任务列表；团队按需展开；任务详情为右侧抽屉（概览 / 依据与权限 / 执行记录）。根页面不滚动，只有对话和列表内部滚动。

**交互规则**

- 闲聊和讨论不强制生成任务；明确的工作请求由超级智能体转为任务，并 @ 对应员工。
- 任务卡链接回原消息；员工在同一对话回报；用户可继续追问和补充，不重置任务。
- 由邮件 / 日期触发的实例，在指挥室显示“由邮件 / 日期触发”消息并链接实例。
- 实时推送用 SSE；断线重连后补齐缺失消息。
- 输入草稿在异步消息到达时不被清除；切换身份不泄露草稿。
- 员工只能看到自己参与的房间和自己负责的任务；负责人可看团队房间。

**状态**

- 消息：发送中 → 已送达 → 失败（可重发）。
- 任务：已分派 → 处理中 → 等待（前置 / 连接 / 资料 / 工具 / 授权 / 审批）→ 已回报 → 已复核 / 已拒绝 / 已取消；另有“结果不明”。

**异常**

| 情况 | 处理 |
|---|---|
| SSE 断线 | 前端自动重连，按最后收到的消息 ID 补齐，不重复显示 |
| 消息发送失败 | 保留输入内容，标“发送失败”，可重发；重发带同一客户端消息 ID，服务端去重 |
| @ 的员工离线或暂停 | 任务照常创建并标“等待连接”，对话里说明原因 |
| 模型不可用或达上限 | 超级智能体回复“暂时无法处理”，任务不丢，进入“等待模型” |
| 请求超出权限（如员工要求查看别人的项目） | 超级智能体拒绝并说明，不创建任务 |

**验收标准**

1. “你好”只得到回复，不生成任务。
2. “@销售员工 整理询价草稿”生成任务，任务卡可跳回原消息，员工回报出现在同一对话。
3. 刷新页面后对话、任务状态完整保留（与原型不同：生产必须持久化）。
4. 断网 30 秒后恢复，期间的消息全部补齐且不重复。
5. 同一条消息重发两次，服务端只记录一次。
6. 员工账号看不到其他员工负责的任务。

### 3.8 待我处理（人工工作项）

**用户故事：** 作为员工，所有需要我核对、决定、亲自完成的事集中在一处，按截止时间排好，每件事告诉我为什么需要我、下一步是什么。

**7 类工作项**

| 类型 | 人要做什么 | 完成证据 | 什么会使之失效 |
|---|---|---|---|
| 数据核对与修正 | 核对拟写入值 | 字段修订与确认的载荷版本 | 拟写值 / 来源 / 目标记录变化 |
| 精确动作批准 | 授权一次确定的动作 | 有权人员对对象 + 参数 + 载荷哈希的决定 | 参数、附件、账号、范围、政策、有效期变化 |
| 人工执行并回填 | 在外部系统亲自完成 | 操作编号或凭证；无法核验时标“人工报告” | 凭证撤回或与外部状态冲突 |
| 正常分支选择 | 选择流程路径 | 决定人、依据、适用规则 | 决定撤回或关键事实变化 |
| 例外裁定 | 处理冲突 / 无依据 | 裁定理由与允许范围 | 新资料推翻事实或超出范围 |
| 补资料 | 补齐缺项 | 资料齐全并核验 | 资料撤回或仍缺必需项 |
| 成果复核 | 判断交付是否合格 | 逐项复核记录与被接受的版本 | 交付或完成条件变化 |

**统一外壳：** 目标系统、对象身份、动作、风险等级、为什么需要人（引用规则）、截止时间、责任人、等待对象。

**4 种渲染器**

1. 字段差异卡：字段、当前值 → 拟写值、来源定位、校验结果，可逐字段修改。
2. 批量明细表：例外排前，先给汇总（共 N · 干净 N · 例外 N），只批准勾选的干净行。
3. 邮件 / 文档预览：收件人、CC、正文（AI 填入处高亮）、附件清单、原来件引用。
4. 问题清单：问题 → 定位 → 依据 → 建议 → 责任人。

渲染器由工具契约的字段声明 + 界面配置（标签、顺序、分组、可编辑性）驱动；复杂业务允许注册专用视图。

**列表：** 默认分组“需要我行动 / 等待外部 / 内部未完”，组内按截止时间排序；可按项目、类型筛选。员工只看自己的；负责人可看团队；“异常视角”只看例外项，不接管日常工作。

**关键规则**

- 批准只改变决定状态，不等于执行；执行前重新鉴权、核对对象版本。
- 提交超时进入“结果不明”，只能回读或人工核查，不提供“再次提交”。
- 执行后回读：拟写值与系统实际值一致才算完成；不一致进入例外裁定。
- 双人复核和金额门槛可配置（SOP 节点级）。
- 质量复核不授予外发、付款或写入权限。

**状态**

- 工作项：待处理 → 处理中 → 待补充 → 已决定 → 已关闭；任一状态 → 已过期 / 已撤回（依据失效时）。
- 关联动作：未提交 → 执行中 → 已确认 / 失败 / 结果不明。
- 二者分开记录：工作项“已决定”不代表动作“已确认”。

**异常**

| 情况 | 处理 |
|---|---|
| 处理期间对象或载荷被他人修改 | 提交决定时校验版本；不一致则拒绝并提示刷新 |
| 两人同时处理同一工作项 | 先提交者生效；后提交者收到冲突提示 |
| 超过截止时间 | 标“已逾期”，通知责任人与负责人；不自动替人决定 |
| 批准后、执行前权限被撤销 | 执行前重新鉴权失败，动作不提交，工作项回到“待处理” |
| 回读与拟写值不一致 | 自动生成例外裁定工作项，原动作标“不一致” |

**验收标准（与原型 T-30 的 59 项专项对应，生产需全部在服务端实现）**

1. 修改金额后，原批准失效。
2. 超时后提交次数保持 1，没有重提按钮。
3. 批次只执行勾选的干净行，例外行保留。
4. 人工回填凭证不显示为“系统已核验”。
5. 不同角色看到的工作项严格按服务端权限过滤（不只是前端隐藏）。
6. 两个浏览器同时批准同一工作项，只有一个生效。
7. 批准后撤销审批人的权限，再执行时动作不会提交。

### 3.9 审计与管理设置

**用户故事**

- 作为负责人，我能查到任何一个结果是谁、在什么时候、依据哪个版本做出来的。
- 作为管理员，我能管理谁能登录、是什么角色、能看哪些项目，并看到系统各部分是否正常。

**页面与交互**（管理设置）

1. 审计：按对象、人员、时间、动作类型筛选；点开看详情（前后值、版本引用、关联任务）；导出 CSV。
2. 用户与角色：列出 Entra 登录过的用户，分配角色和项目范围；停用用户。
3. 部署健康：数据库、Blob、Key Vault、模型服务商、worker 心跳与队列积压、死信数量、browser worker、工具沙箱，各显示正常 / 降级 / 故障和最后检查时间。
4. 数据保留：分别设置审计、执行轨迹、录制截图的保留期。

**业务规则**

- 审计记录：谁、何时、对什么对象、做了什么、依据哪个版本、结果。模型调用、工具调用、外部请求、审批、知识确认、配置修改全部记录。
- 审计只追加，应用账号没有修改和删除权限（数据库层面用独立的只追加角色）；到期清理由单独的保留任务按策略执行，清理本身也写审计。
- 审计正文不含 Key、密码或令牌；敏感字段按工具契约打码。
- 角色来源：Entra App Roles 或平台内配置【待定】；无论哪种，服务端每次请求都按角色和项目范围鉴权。
- 至少保留一名管理员，系统不允许停用最后一名管理员。

**状态**

- 用户：已邀请 → 活跃 → 已停用。
- 组件健康：正常 / 降级 / 故障。
- 导出任务：排队 → 生成中 → 可下载（限时链接）→ 已过期。

**异常**

| 情况 | 处理 |
|---|---|
| 审计写入失败 | 对应业务动作不提交（审计与业务写入在同一事务，外部动作先写审计意图再调用）|
| 健康检查连续失败 | 告警发到 Application Insights 并通知管理员；worker 故障时队列积压在健康页显示 |
| 用户在 Entra 被禁用 | 下次请求时会话失效，进行中的个人工作项转回负责人 |
| 导出数据量过大 | 分批生成，后台任务完成后通知 |

**验收标准**

1. 任意一个工具调用都能在审计里查到调用者、员工、工具版本、载荷哈希、结果。
2. 应用账号直接对审计表执行 UPDATE / DELETE 被数据库拒绝。
3. 审计导出文件中搜索不到 Key 或密码原文。
4. 停用最后一名管理员的操作被拒绝。
5. 停掉 worker 后，健康页在一分钟内显示 worker 故障和队列积压。

## 4. 原型与生产的差异清单

| 原型（v9–v11）中模拟的 | 生产必须真实实现 |

| 前端过滤“待我处理” | 服务端过滤与动作级授权 |
| 无费用计量 | 模型 token 计量与上限 |

## 5. 技术架构

### 5.1 总体结构：一个镜像，三种运行角色

```text
                    ┌──────────── Azure Container Apps 环境 ────────────┐
用户浏览器 ──HTTPS──▶│ web    (APP_ROLE=web)     前端静态资源 + REST API + SSE │
                    │ worker (APP_ROLE=worker)  工作流推进 / 调度 / 同步 / 模型调用 │
                    │ browser(APP_ROLE=browser) Playwright 录制与回放（第二批）   │
                    └───────┬───────────┬───────────┬──────────┬──────────┘
                            │           │           │          │
                     PostgreSQL     Blob Storage  Key Vault   App Insights
                     (+pgvector,    (原文/附件/    (模型Key/   (日志/指标/
                      队列)          截图/产物)     连接凭据)   告警)
                            │
          外部：模型服务商（Anthropic / OpenAI / Azure OpenAI）、Microsoft Graph、客户只读数据库
```

- 同一代码库产出两个镜像标签：`superagent:<ver>`（web + worker）与 `superagent:<ver>-browser`（额外包含 Chromium 与 Playwright，约大 1GB）。不需要录制功能的客户只部署前者。
- “一个镜像”指同一套代码和镜像，不是只跑一个容器：web 与 worker 是两个独立的 Container App，靠 `APP_ROLE` 区分启动命令，各自扩缩容。
- 长任务、知识同步、调度和浏览器执行不能依附 HTTP 请求的生命周期，全部在 worker 中运行。
- worker 是常驻进程，`minReplicas ≥ 1`。原因：Container Apps 在关闭入口、且没有最小副本数或自定义扩缩规则时会缩到 0，并且不会自行启动。Container Apps Jobs 只用于一次性、计划性或事件触发的任务（如数据库迁移），且任务要能安全地被执行至少一次。web 可以按流量缩容，不影响后台工作。

### 5.2 技术栈建议

| 层 | 选型 | 理由 |
|---|---|---|
| 语言 | TypeScript（前后端统一） | 共享类型；与原型和 MCP SDK 生态一致 |
| 前端 | React + Vite，构建为静态资源由后端托管 | 前后端一体，单镜像 |
| 后端 | Node.js 22 LTS + Fastify | 轻量、性能好、插件化 |
| ORM / 迁移 | Drizzle ORM（或 Prisma）【待定】 | 类型安全，迁移脚本进镜像启动流程 |
| 任务队列 / 调度 | pg-boss（基于 PostgreSQL） | 不增加服务；支持重试、延迟、定时 |
| 实时 | SSE | 简单，适合单向推送；断线补齐 |
| 认证 | Entra ID（OIDC，MSAL） | 企业 SSO |
| 模型 SDK | Anthropic SDK、OpenAI SDK（含 Azure OpenAI） | 官方 SDK |
| 工具协议 | MCP（@modelcontextprotocol/sdk） | 接入现成工具生态 |
| 检索 | MVP：PostgreSQL 关键词检索（pg_trgm + 全文）；增强：pgvector + 服务商嵌入或本地嵌入（需评测后启用） | 一个 Claude Key 也能做检索，且不增加镜像体积 |
| 浏览器自动化 | Playwright（browser 角色） | 录制与回放 |

```text
    sandbox/           工具沙箱的启动、凭据临时下发、产物摘要校验（沙箱本身在独立身份的容器中运行）
  web/                 React 前端
packages/
  shared/              类型、契约 schema、常量
```

### 5.4 模型服务商抽象层

```ts
interface LlmProvider {
  id: 'anthropic' | 'openai' | 'azure-openai';
  listModels(): Promise<ModelInfo[]>;                       // 实时拉取
  chat(req: ChatRequest): Promise<ChatResponse>;            // 支持工具调用与流式
  structured<T>(req: ChatRequest, schema: JsonSchema): Promise<T>;  // 结构化输出
  embed?(texts: string[]): Promise<number[][]>;             // Anthropic 无此方法
  usage(resp: ChatResponse): { inputTokens: number; outputTokens: number };
}
```

- 业务代码只调用抽象层，不直接依赖某家 SDK。
- 每次调用前检查月度上限与单任务上限；调用后写计量。
- 工具调用统一转换为内部格式，再交给工具网关执行；模型永远不直接持有凭据。
- 检索：`RetrievalProvider` 独立配置，默认关键词检索；可选服务商嵌入或本地嵌入；切换时全量重建索引。
- 能力白名单：`model_capabilities` 记录每个模型 ID 通过的能力测试与测试日期；业务调用前检查所需能力（如工具调用）。

### 5.7 工作流持久化、幂等与对账

- 队列基于 PostgreSQL：领取用 `SELECT … FOR UPDATE SKIP LOCKED`，避免多个 worker 抢同一任务。
- 任务领取用租约（lease_owner + lease_until + attempt）加心跳续租；worker 崩溃后租约过期，任务重新领取。
- 重试有上限和退避；超过上限的任务进入死信（dead-letter）状态，生成人工工作项，不无限重试。
- 每个外部动作生成幂等键（tenant + instance + step + attempt 无关的业务键），写入 action_requests 后再调用外部系统（outbox 模式）。
- 外部调用超时：状态置“结果不明”，进入回读或人工核查；禁止自动重试写操作。
- 回读：按工具契约中的回读结构查询外部系统，比较拟写值与实际值。
- 定时触发：调度器持久化“名义发生点”，宕机恢复后按补跑窗口与重叠策略处理。

### 6.2 身份与网络

- web / worker 使用用户分配的托管身份访问 Key Vault、Blob、PostgreSQL（PostgreSQL 用 Entra 认证）。
- 镜像和环境变量中不放任何密钥；启动时从 Key Vault 读取。
- 生产：Container Apps 环境接入 VNet；PostgreSQL、Key Vault、Blob 用私有终结点；只有 web 对外。
- browser worker 与工具沙箱使用各自独立的托管身份，不授予主应用 Key Vault 和主数据库访问权；网络出口只允许获准的目标系统域名。

### 6.3 环境与 CI/CD

- 环境：dev、staging、prod，各自独立资源组与 Key Vault。
- 流水线（GitHub Actions 或 Azure DevOps）：测试 → 构建镜像 → 推送 ACR → 部署 staging 新版本（revision）→ 冒烟测试 → 人工批准 → prod 切流量；失败一键回滚到上一 revision。
- 数据库迁移：作为 Container Apps Job 在新版本切流量前执行；迁移必须向后兼容一个版本。
- 基础设施即代码：Bicep（或 Terraform）【待定】，一条命令创建全部必需资源。

### 6.4 交付给客户的部署包

1. Bicep 模板 + 参数文件。
2. 镜像地址与版本。
3. 部署手册：创建资源 → Entra 应用注册 → 首次启动 → 进入 Setup 填 Key。
4. 客户 DBA 手册：如何为只读数据库来源创建只读账号与视图。

## 7. 安全与合规

### 7.1 密钥与凭据

- 模型 Key、数据库凭据、OAuth 刷新令牌只存 Key Vault；数据库只存引用。
- 凭据不进入模型上下文、日志、审计正文、前端。
- Key 轮换：Setup 支持更换；连接凭据支持更换并重新测试。

### 7.2 权限

- 每个 API 在服务端校验：用户角色 + 项目范围 + 对象归属。
- 数字员工的每次工具调用经网关校验：员工身份快照、工具安装与绑定、契约范围、风险策略、是否需要精确批准。
- 知识源只读三层保证（见 3.2.1）。

### 7.3 审批与动作安全

- 批准绑定载荷哈希；载荷变化即失效。
- 结果不明不自动重试写操作。
- 对外发信、付款、业务系统写入默认需要精确批准（可在 SOP 中对低风险只读动作预授权）。

### 7.4 提示注入防护

- 来自资料、邮件、网页、数据库的文本一律包裹为“数据”，系统提示明确其不具指令效力。
- 模型提出的工具调用必须在员工已安装工具与契约范围内，超出即拒绝。
- 高风险动作永远需要人工批准，不因模型输出而跳过。

### 7.5 数据出境与驻留

- Setup 页明确显示实际处理位置：直连 Anthropic / OpenAI 时内容发往服务商；Azure OpenAI 按部署类型（Global / Data Zone / 区域 Standard）处理；Microsoft Foundry 上的 Claude 要区分 Azure 托管与 Anthropic 托管，后者可能离开 Azure（见 3.1）。不笼统承诺“在 Azure 内处理”。
- 数据库、Blob、日志的区域与模型调用区域分别列出，交付给客户确认。

### 7.6 审计与保留

- 审计日志仅追加；保留期可配置。
- 录制截图与执行轨迹可能含敏感信息：受限访问，单独设置较短保留期。

## 10. 风险与待 Robin 决策事项

### 10.1 待决策

1. 部署模式：每个客户一套独立部署（本文默认），还是做多租户 SaaS？
2. ORM 与基础设施即代码工具：Drizzle 还是 Prisma；Bicep 还是 Terraform。
3. 角色管理：用 Entra App Roles，还是平台内自管？
4. 检索增强方案：MVP 用关键词检索（推荐）；之后加服务商嵌入，还是评测后加本地嵌入。
5. MVP 是否包含浏览器录制（会多一个 browser 镜像与网络配置）。
6. 首个试点客户与试点流程（建议从一个只读、可核对结果的高频流程开始）。

### 10.2 主要风险

| 风险 | 影响 | 应对 |
|---|---|---|
| 关键词检索对同义表达召回不足 | 检索质量一般 | P1 做中英文检索评测；按结果加服务商嵌入或本地嵌入 |
| 服务商新模型与平台不兼容 | 调用失败或工具调用出错 | 能力白名单 + 切换前测试；切换后相关验收待复核 |
| worker 被缩到 0 | 后台任务和定时触发停止 | worker minReplicas = 1，健康页监控队列积压 |
| Azure 区域缺少所需模型或服务 | 不能满足数据驻留 | 部署前逐项核实，写入交付清单 |
| 只读数据库被误配为可写账号 | 数据风险 | 连接测试时检测账号权限，发现写权限则拒绝确认 |
| 网页系统改版导致录制工具失效 | 自动化中断 | 健康检查与熔断，自动降级人工执行并派修复任务 |
| 模型费用超预期 | 成本失控 | 月度与单任务上限，经济模型分流 |
| 单区域单实例 | 区域故障不可用 | MVP 接受；生产按客户要求评估多区域 |
